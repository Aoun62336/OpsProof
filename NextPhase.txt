Implementation begins · Based on OpsProof(2).zip · November 5, 2026

We are moving beyond detecting incidents to a more demanding question:

Can OpsProof investigate a failure, recommend an evidence-backed response, execute a narrowly authorized recovery, and independently establish whether it worked?

That is the objective of Milestone 4.
1. What the existing code supports
I reviewed the source again before planning the implementation. Your current system already has:
- A PostgreSQL-backed incident registry with deduplicated firing/resolved alert transitions.
- A control API with API-key authentication, browser sessions and CSRF protection.
- An independent action worker and evidence worker connected through Redis Streams and a transactional outbox.
- A bounded queue-burst experiment that creates demo jobs and verifies their final states.
- Prometheus metrics for API requests, dependencies, experiment states and demo job states.
- The approved Forest & Porcelain interface, including the Incidents page.
We will extend those components rather than introduce a second control plane or rebuild the existing application.

There is one prerequisite: the uploaded archive did not independently establish that the complete Milestone 3 alerting and telemetry fault drills passed. We can implement Milestone 4 now, but operational recovery must remain disabled until those integration checks pass.
2. The architecture we will implement
Detected incident

Evidence snapshot

Deterministic diagnosis

Testable rules, no model cost, can abstain


Optional AI diagnosis

Strict allowlist, current evidence, expiry, kill switch


Restricted action worker → Independent evidence worker

Execute bounded operation → verify actual outcome → preserve audit trail


The model will never approve or execute an operational action. AI output is a hypothesis to inspect, not an authorization credential.
The initial recovery capability
For the local demo, we will implement a controlled recovery of a deliberately paused background worker. This will use a narrowly scoped demo-only control endpoint rather than mounting /var/run/docker.sock or granting cloud credentials.

The scenario will be:
1. Deliberately pause the demo worker's consumption of new jobs.
2. Create a bounded backlog and observe the corresponding incident.
3. Collect evidence and request a recovery proposal.
4. Require explicit operator approval.
5. Let the restricted action worker resume job consumption.
6. Let the independent evidence worker check that queued jobs actually completed.
7. Record whether recovery was verified, failed or could not be established.
This is a real controlled recovery of a deliberately paused worker, not a claim that OpsProof can restart an arbitrary crashed process. Restarting Kubernetes workloads and progressive rollback will require the restricted Kubernetes permissions introduced in Milestone 5.

Milestone 4: Implementation decisions confirmed
I have now checked the actual source in OpsProof(2).zip, including action.py, evidence.py, streams.py, both FastAPI applications, the incident tables, the Compose networks, and the current React routes.

There are three important corrections to make to the earlier Milestone 4 outline.

First, a paused worker is not the same as a stopped container. Your demo worker currently consumes Redis Streams continuously; it has no pause/resume control. We must implement an explicitly bounded, demo-only pause mechanism before claiming that an operator can recover it. This will not give OpsProof access to the Docker socket.

Second, we must protect the existing experiment pipeline. Your current outbox uses a run_id foreign key to experiments, and the Redis consumer expects experiment UUIDs. We should not insert recovery messages into that structure without changing its contract. Instead, recovery approvals will live in a separate durable PostgreSQL state machine, with the existing restricted workers processing only the work permitted to them.

Third, incident detection is not proof of root cause. A queue-backlog alert establishes that work is waiting; it does not prove the worker is paused. The diagnosis engine must confirm the pause state and the relevant job records before recommending the demo-worker resume action. Otherwise it must abstain.
The safety contract
Boundary	What it can do
Control API	Authenticate operators, create investigations, record approvals and rejections
Evidence worker	Read bounded evidence, run deterministic diagnosis, optionally evaluate AI, verify recovery
Action worker	Execute one allowlisted demo recovery after checking authorization and live state
Demo API	Expose narrowly scoped inspection and idempotent resume operations
AI provider	Produce a structured, untrusted diagnosis hypothesis
PostgreSQL	Persist investigation, approval, execution and verification history
Redis	Hold the temporary, expiring demo-worker pause signal

Recovery will be disabled by default. A valid operator login alone will not execute anything, and an AI suggestion will never bypass a policy check.

This follows OWASP's guidance to enforce least privilege, treat model output as untrusted, and place approval enforcement at the actual action boundary.

Running

Why are credentials separated?
The control API can accept an operator's request but cannot directly call the demo recovery actuator.

The evidence worker can inspect the demo worker and call an optional model provider, but it does not receive the actuator key.

The action worker receives the dedicated actuator key, but not the AI-provider key.

This separation reduces the impact of a compromised component. It does not create complete operating-system-level isolation between all processes, but it is a meaningful enforcement boundary at the service/API level.

                      confirmation !== CONFIRM
                      || approve.isPending
                    }
                    onClick={() => approve.mutate()}
                  >
                    Approve once
                  </button>

                  <button
                    className="button button--secondary"
                    type="button"
                    disabled={reject.isPending}
                    onClick={() => reject.mutate()}
                  >
                    Reject
                  </button>
                </div>
              </div>
            )}

            {recovery.error && (
              <p className="inline-error">
                {recovery.error}
              </p>
            )}

            {recovery.status === "succeeded" && (
              <p className="verified-note">
                <CheckCircle2 size={17} />
                Exact jobs, experiment verification,
                and alert resolution were checked.
              </p>
            )}

            {events.data && events.data.length > 0 && (
              <ol className="recovery-events">
                {events.data.map((event) => (
                  <li key={event.id}>
                    <strong>
                      {titleCase(event.type)}
                    </strong>

                    <time dateTime={event.created_at}>
                      {formatDate(event.created_at)}
                    </time>
                  </li>
                ))}
              </ol>
            )}
          </div>
        )}
      </section>
    </div>
  );
}

Part 16. Measure the real result
Step 60. Establish the measurement boundaries
This milestone gives us a measured operational workflow, but it does not yet justify an invented percentage reduction.

We need to distinguish four times:
Measurement	Definition
Detection delay	First firing incident received minus fault injection
Investigation delay	Diagnosis completed minus investigation requested
Approval-to-action delay	Actuator acknowledgment minus operator approval
Verification delay	Independent recovery verification completed minus action acknowledgment

Also record the time between the fault injection and successful verification as an overall observed recovery-trial duration.

The timestamps have different origins. Fault-injection time comes from your terminal; incident and recovery events come from PostgreSQL.

Because different clocks and process boundaries are involved, verify clock synchronization and use UTC. Do not describe differences of a few milliseconds as precise unless your collection procedure supports that precision.
What is a valid percentage improvement?
Suppose a later controlled comparison shows that one process has a median duration of \(B\) seconds and the improved process has a median of \(N\) seconds.

Then:
\[
\text{Reduction}=\frac{B-N}{B}\times100
\]

But the two procedures must be genuinely comparable.

For example, comparing an automatically expiring eight-minute pause with a manually approved resume is not automatically proof of a percentage improvement in production MTTR. The experiment designs and observation windows differ.

Milestone 6 is where we will run repeatable baseline-versus-improvement comparisons and calculate defensible percentage impacts.

For now, record the actual detection, approval and verification durations, including unsuccessful and inconclusive trials.
